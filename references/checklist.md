# 自检清单 · 每一条在查什么

这份文档解释 `audit.py` 报出的每一条到底在说什么、为什么重要、怎么改。
报告里只有一句话，这里补上背景。

按报告里的编号查就行。

---

## 结构完整性 S-01 ~ S-06

### S-01 缺少一级章节

**查什么**：方案里有没有这八章。

```
1 背景        2 系统概述    3 需求分析      4 目标与原则
5 密码应用设计 6 安全管理    7 合规性分析    8 实施保障
```

**为什么**：这八章是 GB/T 43207-2023 附录 A 规定的骨架，不是可选项。
评审拿到的第一眼就是看章节齐不齐——缺章意味着方案没写完，
后面的技术内容写得再好也会被退回。

**容错**：工具认得出「一、背景」「1. 项目背景」「第一章 背景」这几种写法。
但正文里顺口提一句"背景"不算数，得是标题行或者以章号开头。

**怎么改**：补写缺的章。如果确实不涉及（比如纯内部系统没有实施保障的对外内容），
也要保留这一章，写明"本项目不涉及，原因如下"，不要直接删章。

### S-02 第 2 章子节不全

**查什么**：第 2 章有没有 2.1 到 2.5 五个子节。

**为什么**：系统概述要交代清楚系统边界、业务、用户、网络、数据五件事。
少一件，第 3 章的需求分析就缺少依据，第 5 章的设计就成了空中楼阁。

**怎么改**：补齐 2.1–2.5。这五节是自检时最容易被当成"随便写写"的部分，
但评审恰恰会从系统概述里找破绽——比如用户范围写得含糊，
后面 8.4 a 的身份鉴别强度就没有判断依据。

### S-03 第 3 章子节不全

**查什么**：第 3 章有没有 3.1 到 3.3 三个子节。

**为什么**：需求分析是把"系统长什么样"翻译成"要保护什么"的关键一步。
需保护对象、合规要求、风险分析三块缺一块，第 5 章的设计就没有来源。

**怎么改**：补齐 3.1–3.3。3.1 列出的需保护对象，第 5 章要一一对应有设计——
这条工具只能提示（见 X-01），但人工要自己核。

### S-04 第 5 章子节不全

**查什么**：第 5 章有没有 5.1 到 5.5 五个子节。

**为什么**：设计章是全篇的核心。总体设计、技术架构、详细设计、部署架构、
运行维护，这五节缺哪一节，都得在评审时被追问。

**怎么改**：补齐 5.1–5.5。

### S-05 5.3 九要素不全

**查什么**：第 5.3 节里有没有 a) 到 i) 这九个要素标记。

**为什么**：详细设计要按九个方面展开，漏一个方面等于漏了一类安全需求。
工具只认标记（a) b) ... i)），**不核对这九项的具体名称**——
因为 SPEC 里只规定了编号，没规定每项的固定名称。

**怎么改**：把缺的编号补上，每个编号下写清设计内容。

### S-06 密钥管理环节不全 / 缺密钥管理设计

**查什么**：第 5.3 节里有没有密钥管理，以及它下面有没有十个环节：

```
生成 存储 分发 使用 更新 归档 撤销 备份 恢复 销毁
```

**为什么**：密钥管理是密评里最容易被挑出问题的地方。
十个环节缺任何一个，都会被认为"密钥全生命周期管理不完整"。
这一条工具同时核对**标记（a–j）和环节名称**，两个都要对。

**找不到密钥管理就是 critical**——那是整章缺失，不是少一环。

**怎么改**：补一节密钥管理，十个环节逐个写。每一环至少说清三件事：
谁负责、用什么设备、多久做一次。只写"按规定管理"等于没写。

## 指标覆盖 C-01 ~ C-05

### C-01 未找到指标对照表

**查什么**：全文有没有一张列着条款号的表。

**为什么**：对照表是方案里唯一结构化的地方，也是评审逐条打勾的依据。
没有这张表，方案等于没做自评。

**怎么改**：在第 7 章补一张表，三列就够：条款 / 级别 / 自评结论。

工具**找不到就报，绝不猜**——硬凑出来的覆盖结论比没有更糟。

### C-02 对照表行数不对

**查什么**：表的数据行是不是 41 行（技术 22 + 管理 19）。

**为什么**：行数不够通常意味着指标被合并或漏掉了。

**怎么改**：补齐。不适用也要单独占一行写"不适用"，不要删行、不要合并。

### C-03 技术指标有遗漏

**查什么**：8.1 到 8.4 的 22 条，缺了哪几条。

**为什么**：少一条就是少一项要求，评审会直接扣。

**怎么改**：报告里会列出缺的具体条款号，逐个补。

### C-04 指标级别与标准不一致

**查什么**：级别列写的是不是标准里的「应 / 宜 / 可」。

**为什么**：级别不是风格问题。写"应"就等于承诺必须做到并且要举证；
写"宜"留了余地。把「宜」写成「应」，是自己给自己加难度；
把「应」写成「宜」，是规避要求，评审会当场指出来。

**怎么改**：按标准原文填。报告里会写「条款 X 应为『宜』，方案写的是『应』」。

### C-05 管理部分条款号缺失

**查什么**：表有 41 行，但一条 9.x 条款号都没识别到。

**为什么**：说明管理部分的条款号可能没按 9.x 编号，机器读不出来，
人工核对也会费劲。

**注意**：管理 19 项的逐条核对目前**还没做**——SPEC 没给这 19 项的
条款号和级别。现阶段工具只检查总行数。拿到数据后会补上。

## 表述越位 W-01 ~ W-02

### W-01 / W-02 出现「符合」

**查什么**：正文和表格里有没有「符合」。

**为什么**：「符合」是测评结论，需要有实施证据和测评报告。
方案阶段写「符合」，评审第一句就问「证据呢」。
方案阶段只能说设计层面的话。

**允许的写法**：

```
设计满足 / 满足 / 依赖云商提供 / 待验证 / 部分满足 / 不适用
```

**不会被误报的四种情况**（工具已排除）：

| 写法 | 为什么不报 |
|---|---|
| 不符合 | 意思相反，是如实说明差距 |
| 整改后符合 | 有明确的前置条件 |
| 符合性分析 | 是名词，说的是"分析这件事" |
| 符合 GB/T ×××× | 说的是遵循编写规范，不是对指标的断言 |

后两条是我在 SPEC 之外加的排除项。不加的话，一份正常方案会报出几十条假问题——
章节名「符合性分析」、正文里引用标准，全会中招。报告一旦全是噪音就没人看了。

**怎么改**：把「符合」改成设计层面的说法。确实要保留的，补上依据
（比如"依据××年××月测评报告，结论为符合"）。

## 排版格式 F-01 ~ F-04

这四项**不参与评分**——它们影响观感，不影响内容对错。

### F-01 表格列数不一致

同一张表里，有的行 3 列、有的行 4 列。多半是合并单元格时选错了范围。
打开 Word 看一下那张表就能发现。

### F-02 没有使用 Word 标题样式

文档里有章节名，但一个都没用「标题 1/2/3」样式，全是手打的。

**为什么重要**：手打标题会让自动目录、导航窗格、交叉引用全部失效。
方案动辄几十页，评审想跳到第 5 章只能滚鼠标，体验很差。

**怎么改**：选中标题文字 → 开始 → 样式 → 标题 1（章）/ 标题 2（节）。

### F-03 条款号格式不规范

`8.2b` 和 `8.2-B` 都不对，标准写法是 `8.2 b)`：数字、空格、字母、右括号。

**为什么**：跟标准原文对不上，检索会漏，评审核对时也要多花时间。

### F-04 有占位符没填

`TODO` / `XXX` / `待补充` / `【】` 这类痕迹没清掉。

交出去之前全文搜一遍。方案里留一个 TODO，比少写一段话严重得多——
它说明这份稿子还没定稿就交上来了。

## 附：评分怎么算

```
penalty = 每条 critical 20 分，warn 6 分，hint 0 分
score   = round(100 × e^(−penalty / 90))
有 critical 时，上限 65 分
```

直觉对照：

| 情况 | 大约得分 |
|---|---|
| 一条问题都没有 | 100 |
| 1 条 warn | 94 |
| 3 条 warn | 82 |
| 1 条 critical | 65（封顶） |
| 3 条 critical | 51 |

所以要拿到 80 分以上，warn 不能超过 3 条，且不能有任何 critical。
