# GB/T 39786-2021 第三级 · 指标速查

> **用途**：写方案时按这张表逐条对，写完拿 `audit.py` 跑一遍看漏没漏。
>
> **边界**：这张表是速查用的，条款号和级别照 GB/T 39786-2021 抄，
> 「检查什么」一列是按密评实践归纳的提示，**不是标准原文**。
> 正式判定一律以标准正文为准。级别（应/宜/可）不能自行升降——
> 应、宜、可分别对应"必须做 / 正常情况下应该做 / 可以做也可以不做"，
> 改级别就等于改了要求。

## 一、技术部分 22 项（第 8 章）

第三级的技术要求分四层，每层条目数不同，加起来正好 22 项：

| 层 | 条款 | 条数 |
|---|---|---|
| 物理和环境安全 | 8.1 | 3 |
| 网络和通信安全 | 8.2 | 5 |
| 设备和计算安全 | 8.3 | 6 |
| 应用和数据安全 | 8.4 | 8 |
| **合计** | | **22** |

### 8.1 物理和环境安全（3 项）

| 条款 | 级别 | 检查什么 |
|---|---|---|
| 8.1 a | 宜 | 电子门禁记录数据的存储完整性——门禁记录有没有被改过的可能 |
| 8.1 b | 宜 | 视频监控记录数据的存储完整性——录像能不能被篡改 |
| 8.1 c | 宜 | 密码模块的合规性——用的密码模块是否满足相应等级要求 |

**三级注意**：这一层三项全是「宜」，没有「应」。
三级方案里如果这一层一个密码措施都没写，不算硬伤，但要在文中说明理由；
反过来，如果写成「应」就是级别拔高，评审会问依据。

### 8.2 网络和通信安全（5 项）

| 条款 | 级别 | 检查什么 |
|---|---|---|
| 8.2 a | 应 | 通信实体身份鉴别——谁在连我，凭什么证明 |
| 8.2 b | 宜 | 通信数据完整性——传过去的报文有没有被动过 |
| 8.2 c | 应 | 通信过程中重要数据的机密性——敏感内容会不会被中途看到 |
| 8.2 d | 宜 | 网络边界访问控制信息的完整性——ACL、策略这些能不能被改 |
| 8.2 e | 可 | 安全接入认证——非受控终端接进来的认证 |

**三级注意**：a 和 c 是「应」，这两项没有对应设计就是硬缺口。
8.2 b 是「宜」但实际评审里经常被追问，方案里写了比不写省事。

### 8.3 设备和计算安全（6 项）

| 条款 | 级别 | 检查什么 |
|---|---|---|
| 8.3 a | 应 | 设备身份鉴别——登录设备时的身份认证 |
| 8.3 b | 应 | 远程管理通道安全——运维通道有没有加密和认证 |
| 8.3 c | 宜 | 系统资源访问控制信息完整性 |
| 8.3 d | 宜 | 重要信息资源安全标记完整性 |
| 8.3 e | 宜 | 日志记录完整性——审计日志能不能被篡改 |
| 8.3 f | 宜 | 重要执行程序或数据文件的完整性 |

**三级注意**：a、b 是「应」。8.3 b 是三级最常被漏的一项——
很多方案写了应用层加密，却忘了运维人员是怎么登服务器的。

### 8.4 应用和数据安全（8 项）

| 条款 | 级别 | 检查什么 |
|---|---|---|
| 8.4 a | 应 | 应用层身份鉴别——用户登录的强度（是否多因素） |
| 8.4 b | 宜 | 访问控制信息的完整性 |
| 8.4 c | 宜 | 重要信息资源安全标记完整性 |
| 8.4 d | 应 | 重要数据传输的机密性 |
| 8.4 e | 应 | 重要数据存储的机密性 |
| 8.4 f | 宜 | 重要数据的完整性 |
| 8.4 g | 宜 | 日志记录完整性 |
| 8.4 h | 宜 | 不可否认性——签名、时间戳这类能证明"做过"的措施 |

**三级注意**：a、d、e 是「应」，这三项是三级方案的核心得分点。
8.4 h 只有存在留证类业务（签名、出证、批复、合同）时才真正适用，
不涉及的写「不适用」并说明业务上没有这类场景，不要空着。

## 三、41 行对照表怎么排

方案第 7 章（合规性分析）里那张表，行数和结构是有讲究的：

```
技术部分 22 行   ← 第 8 章，按 8.1 → 8.4 顺序
管理部分 19 行   ← 第 9 章
合计      41 行
```

**每条一行，不合并**。同一层里 a)、b)、c) 各占一行，不要写成「8.1 a-c 共三项」。

原因很实际：合并之后：

1. 漏了哪一项看不出来——整行打勾就过去了
2. 级别没法逐条对应——a 是「宜」、c 是「应」，合并成一行写哪个都不对
3. 机器读不出来——`audit.py` 靠条款号逐条比对，合并行会被当成缺失

**不适用的怎么办**：也要单独占一行，自评栏写「不适用」并说明理由，
不要直接删掉那一行。删了之后别人无法判断是"不适用"还是"忘了写"。

## 四、自评栏能写什么

方案阶段只能下设计层面的结论。允许的写法：

| 写法 | 什么时候用 |
|---|---|
| 设计满足 | 方案里已经有对应的设计，且技术路线清楚 |
| 满足 | 同上，简写 |
| 依赖云商提供 | 用的是云平台的密码能力，责任在云服务商 |
| 待验证 | 设计了但需要实施后验证，方案阶段给不出证据 |
| 部分满足 | 只覆盖了一部分场景，剩下的在文中说明 |
| 不适用 | 业务上没有这个场景 |

**不能写「符合」**。「符合」是测评结论，要有实施证据和测评报告支撑，
方案阶段写这个词，评审第一件事就是问证据在哪。

`audit.py` 的 W-01 / W-02 就是查这个。判定时排除了四种情况
（不符合 / 整改后符合 / 符合性 / 符合 GB/T ××××），
所以你写「目前不符合，整改后符合」不会被误报。

## 五、密钥管理的十个环节

三级方案必须写到这十个环节，缺一个就是结构缺陷
（`audit.py` 的 S-06 查这个）：

```
生成 → 存储 → 分发 → 使用 → 更新 → 归档 → 撤销 → 备份 → 恢复 → 销毁
```

写法上每一环至少要说清三件事：**谁负责、用什么设备、多久做一次**。
只写"密钥按规定管理"这种话，等于没写。
